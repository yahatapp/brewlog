# 認証フロー

このドキュメントでは、IDトークンを利用した独自の認証・認可フローについて記述します。

## 概要
LIFFアプリから取得できる IDトークンを利用し、バックエンド (Hono) で直接検証を行う軽量な認証方式を採用します。
Supabase Auth の外部プロバイダー連携は利用せず、DB上の `profiles` テーブルでユーザーを管理します。

## 認証シーケンス

1.  **初期化:**
    - フロントエンドで `liff.init()` を実行。
2.  **トークン取得:**
    - `const idToken = liff.getIDToken()` で IDトークンを取得。
3.  **APIリクエスト:**
    - Hono RPC クライアントの Header に `Authorization: Bearer <idToken>` を付与してリクエスト。
4.  **バックエンド検証 (Middleware):**
    - Hono 側で以下のいずれかの方法で検証：
      - **A: LINE検証APIを利用** (`https://api.line.me/oauth2/v2.1/verify` へ POST)
      - **B: 公開鍵による署名検証** (エッジでのパフォーマンスを重視する場合)
    - トークンが有効であれば、ペイロードから `sub` (LINEのユーザー一意識別子) を取得。
5.  **コンテキスト保持:**
    - `c.set('lineUserId', sub)` として、後続のハンドラーで利用可能にする。

## ユーザー管理
- `profiles` テーブルに `line_user_id` (unique) カラムを持ち、初回ログイン時に自動でレコードを作成する（ユーザー登録）。
- 以降のデータ操作（コーヒー豆の登録など）は、この `line_user_id` を外部キーとして利用する。

## メリット
- リダイレクトが発生しないため、アプリの起動が極めて速い。
- Supabase Auth の複雑な設定が不要。
- 個人/夫婦利用には十分なセキュリティ。

## アクセス制限 (Allowlist)
不特定多数からのアクセスを防ぐため、バックエンド (Hono) で Allowlist 方式による制限を設けます。

1.  **許可リストの管理:**
    - 環境変数 (`ALLOWED_LINE_USER_IDS`) または DB に、利用を許可するユーザーの `sub` (LINEユーザーID) を登録しておく。
2.  **検証プロセス:**
    - 認証ミドルウェアで IDトークンを検証した後、取得した `sub` が許可リストに含まれているかチェック。
3.  **拒否:**
    - リストに含まれていないユーザーからのリクエストには `403 Forbidden` を返し、アプリの利用を拒否する。

これにより、公式アカウントが万が一検索などで見つかっても、開発者（夫婦）以外はデータを閲覧・操作できない安全な環境を維持します。
